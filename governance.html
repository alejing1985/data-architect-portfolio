01
FAIR principles —
applied, not just cited
Findable · Accessible · Interoperable · Reusable
How I use FAIR
"I use FAIR both as a conceptual guide and as a practical checklist when designing data products. The question for each principle is not 'do we comply?' but 'what would break this?' — that's where the real governance decisions live."
F
Findable
Data and metadata must be registered and indexed so they can be discovered by both humans and machines — even if they can't access the data itself.
In practice: every data product registered in the catalog (Atlan / Purview) with standardized metadata — name, domain, owner, description, tags. Naming conventions enforced by DevOps pipelines so search works consistently across all products.
A
Accessible
Data should be retrievable by anyone with the appropriate authorization, using open and standardized protocols — even if the data itself is restricted.
In practice: role-based access control in Snowflake provisioned via Terraform — least privilege by design. Each data product has its own read roles. Access is requested through a defined process, not granted ad hoc. Metadata remains accessible even when data is restricted.
Hardest to achieve
I
Interoperable
Data should use shared vocabularies, formats and standards so it can be integrated with other data and systems without custom transformation for each case.
In practice: this is the hardest principle because it depends on business alignment, not technology. A shared vocabulary requires that Marketing and Finance agree on what "active customer" means before any data product can claim to be interoperable. Open formats (Parquet, Iceberg) help at the technical layer — but shared semantics require organizational governance that no tool can enforce alone.
R
Reusable
Data and metadata should be richly described so they can be replicated and combined across different contexts, with clear usage licenses and provenance.
In practice: data product templates document provenance (sources, transformations applied, known limitations). dbt documentation generates lineage automatically. Silver Master data products are designed explicitly for reuse across multiple Gold products — reusability is a design criterion, not an afterthought.
Why Interoperability is the hardest FAIR principle
The technical layer of interoperability — open formats, standard APIs, common protocols — is solved. What's not solved is the shared vocabulary: the agreement between business domains on what entities mean, how they're measured, and how they relate to each other.

This is a governance and organizational problem, not a technology problem. You can build the most technically interoperable data platform in the world and still have four teams reporting four different "revenue" numbers because no one aligned on the definition. The semantic layer (dbt Semantic Layer, Atlan business glossary) helps — but it only works if the business participates in building it, which requires management alignment and dedicated effort that most organizations underestimate.
02
Governance as code —
enforcement over documentation
Standards that live in pipelines, not in wikis
The core principle
"A naming convention that lives in a Confluence page is a suggestion. A naming convention validated in a CI/CD gate before every merge is governance. The difference is enforcement — and enforcement only scales when it's automated."
Layer
What it governs and how
Status
Naming conventions
Automated validation in Azure DevOps CI pipelines before any PR can merge. Applies to Data Factory pipelines, Snowflake objects (databases, schemas, tables) and dbt models. A non-compliant name fails the build — not a review comment, a build failure.
Implemented
Approval policies
Differentiated approval rules by impact level in Azure DevOps. Silver Master changes require additional approval beyond the standard PR review, given their downstream impact on multiple data products. Changes to Bronze ingestion patterns require infrastructure team sign-off.
Implemented
Infrastructure as code
Snowflake databases provisioned as data products via Terraform through Azure DevOps pipelines. Each domain and subdomain gets its own database with standardized naming, consistent RBAC roles, and the same permissions across dev, staging and prod — generated from the same Terraform module, not configured manually.
Implemented
Tagging policies
Mandatory resource tags (domain, environment, data product) validated in the Terraform plan before any Azure resource deploys. Resources without required tags fail the deployment — the FinOps cost attribution loop is enforced at infrastructure level. Adoption across all teams and resources is still being consolidated.
In progress
dbt quality tests
dbt's native testing framework (not_null, unique, accepted_values, relationships) allows automated data quality checks to run as part of the transformation pipeline. A model with failing tests should not promote to production. This is a known gap in our current implementation — tests exist in isolated models but are not yet consistently enforced across all data products as a pipeline gate.
Known gap
Data contracts
Currently formalized as Excel templates documenting schema, SLA, owner, sources and consumers per data product. The target state is YAML-based contracts versioned in the same repository as the dbt models — enabling contract validation as part of the CI/CD pipeline and breaking change detection before deployment.
In progress
03
Data contracts —
from Excel to YAML
Formalizing the agreement between producers and consumers
What a data contract is
A data contract is an explicit, versioned agreement between a data product producer and its consumers that defines what the producer promises to deliver: schema, data quality levels, freshness SLA, availability, and how breaking changes will be communicated.

Without a contract, the producer and consumer have implicit assumptions that only surface as incidents. With a contract, breaking changes are caught before they reach production — and when they do reach production, everyone knows who is accountable.
Where we are — Excel templates
We formalized data contracts as Excel templates to allow non-technical stakeholders to participate in definition before the tooling was ready. Each template documents:

· Product name and domain / subdomain
· Owner — named person, not a team
· Schema — field names, types, descriptions
· Sources — upstream dependencies
· Consumers — who depends on this product
· SLA — freshness, completeness, availability targets

This was a pragmatic first step. The limitation: contracts in Excel are not versionable, not machine-readable, and not enforceable in a pipeline.
Target state — YAML data contract (best practices)
A YAML data contract lives in the same repository as the dbt model it describes. It is versioned, diffable, and can be validated automatically in CI before a breaking change reaches production. A well-structured contract looks like this:
# data-contract: customer_master_silver
version: 2.1.0
domain: customer
layer: silver_master
owner: data-platform-team

sla:
  freshness: daily · max 6h delay
  completeness: > 99.5% non-null on PK
  availability: 99.9%

schema:
  - name: customer_id
    type: VARCHAR  # business key · never null
  - name: status
    type: VARCHAR
    accepted_values: [active, inactive, pending]

consumers:
  - gold.customer_insights
  - gold.churn_analysis

breaking_change_policy: semver · 30-day deprecation notice
Best practices for data contracts in YAML
01
Use semantic versioning
Major version (2.0.0) for breaking changes — field removed, type changed, key renamed. Minor (2.1.0) for backwards-compatible additions — new field added. Patch (2.1.1) for fixes. Consumers subscribe to a major version, not a file path.
02
Co-locate with the dbt model
The contract file lives in the same directory as the dbt model it describes. When a developer changes the model, the contract is right there — impossible to forget to update. A CI gate fails the PR if the contract version wasn't bumped on a schema change.
03
Declare consumers explicitly
Every downstream data product that depends on this one is listed in the contract. This makes impact analysis automatic — before changing a Silver Master, the pipeline can check all declared consumers and flag the change. No more discovering breaking changes in production.
04
Define SLAs as testable assertions
SLAs should be specific enough to be verified automatically. "Data is fresh" is not testable. "Max 6-hour delay from source timestamp to available in Silver, verified at 08:00 UTC daily" is testable — and can be wired to an alert if it fails.
05
Separate physical schema from semantic contract
The contract documents what the field means, not just its type. A VARCHAR called "status" with accepted_values [active, inactive, pending] is a semantic contract. This is what connects FAIR's Interoperable principle to actual code — the shared vocabulary lives in the contract, not just in a glossary.
06
Start with Silver Master products
Not all data products need a formal YAML contract immediately. Prioritize Silver Masters first — they have multiple consumers, so the cost of a breaking change is highest. Once the pattern is established, extend to Gold products and then Source products.

Tooling — Purview vs Atlan
Two governance platforms, two different contexts
The decision frame
"Both Purview and Atlan are governance platforms. The right choice is not which one is better — it's which one fits your stack. If you live in the Microsoft ecosystem, Purview's native integrations are hard to beat. If your platform is multi-cloud or Snowflake-first, Atlan's cross-platform lineage and dbt integration make it the stronger choice."
Microsoft Purview
Platform 01 · Azure-native stack
Strengths
Native integration with the entire Azure ecosystem — Synapse, ADF, ADLS, Azure SQL — lineage is automatic with zero configuration for Microsoft services.
Deep integration with Microsoft 365 and sensitivity labels — governance extends beyond data to documents and emails in the same console.
Policy enforcement at the storage level — can restrict access to ADLS containers directly from Purview, not just catalog metadata.
Strong choice when the entire stack is Microsoft — the integration depth is unmatched in that context.
Limitations
When I started using it, it was early-stage — the product has evolved significantly since, but that initial experience shaped my perception.
Outside the Microsoft ecosystem, integration effort increases substantially. Non-Azure sources require custom connectors or manual lineage.
Less mature workflow and collaboration features compared to Atlan — business glossary and stewardship workflows are more limited.
Atlan
Platform 02 · Snowflake + dbt stack
Strengths
Native dbt integration — lineage is generated automatically from dbt metadata, column-level, without manual configuration. The lineage graph shows exactly how a Gold model traces back to source.
Deep Snowflake integration — query history, table statistics, and usage patterns surfaced directly in the catalog without additional instrumentation.
Richer collaboration and governance workflows — data stewardship, request access, certification workflows are more mature.
Cross-platform by design — works across cloud providers and tools without being tied to one vendor's ecosystem.
Limitations
Higher license cost than alternatives — the ROI depends on the team actually using the catalog, which requires adoption effort.
Data quality capabilities are not its strongest suit. In my experience, Purview was ahead in this area — not top-tier either, but more developed at the time of comparison. If data quality enforcement is the primary need, a dedicated tool may serve better than either platform.
Outside of its supported connectors, integration effort is similar to any other catalog — the advantage disappears when the stack diverges from its core integrations.
How to choose — a simple decision frame
This reflects my experience with both tools at a specific point in time. Both products evolve continuously. Any tooling decision should be grounded in current hands-on evaluation, not past experience or cost alone.
Choose Purview when
Your entire stack is Microsoft — Azure, Synapse, ADF, Fabric. You need sensitivity label integration with M365. The automatic lineage across Microsoft services alone justifies the choice. Relatively stronger in data quality enforcement compared to pure governance catalog alternatives.
Choose Atlan when
Your stack is Snowflake + dbt, multi-cloud, or you need rich cross-platform lineage. The dbt integration — automatic column-level lineage from model code — makes it the stronger choice for modern data platforms focused on governance and discoverability.
If data quality is the priority
Neither Purview nor Atlan are primarily data quality tools. If DQ enforcement is the core requirement — not just cataloging — a dedicated data quality platform may serve better. The decision should be driven by current business needs and the company's data roadmap, not by tool names or license cost alone.
