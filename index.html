Design principles
01
Architecture is a function of the organization, not the other way around
The best architecture is not the most advanced one — it's the one the company can actually operate. I design based on available tooling, business needs, growth trajectory, and — critically — team skill set. A platform the team can't own will fail regardless of how well it's designed on paper.
02
Build for evolution, not for the final state
I design modular, decoupled architectures where components can be replaced, upgraded or retired with the least possible impact on the rest of the system. Tight coupling is the single largest barrier to change I've encountered in every migration. Decoupling is not a nice-to-have — it's a prerequisite for longevity.
03
Stay current, choose deliberately
I follow architectural trends and tooling closely — not to adopt everything new, but to make informed trade-offs. Knowing what exists in the ecosystem is what separates a deliberate architectural decision from a default one. The goal is to pick the right tool for the actual context, not the most popular one.

Azure · CAF Landing Zones · Delta Lake · Medallion Architecture · FinOps · IaC
From centralized sandbox to a distributed
platform oriented around data products
Full redesign of an Azure platform adopting Microsoft's Cloud Adoption Framework, a centralized-federated model with Data Mesh principles, Delta Lake over ADLS Gen2, and Synapse Serverless. Designed to scale toward self-service without a redesign.
The problem
The original platform was a centralized Azure sandbox: a single shared environment with costs impossible to attribute by domain. The critical structural issue was that the Silver and Gold layers were tightly coupled — any change to one broke the other, making migration to a new model extremely risky.
Model adopted
Centralized-Federated · Data Mesh principles
Data Mesh was not adopted 100% — the organization lacked the maturity for fully distributed self-service. The data team builds all data products centrally, but the architecture is designed so domains can assume ownership without a redesign when ready. Self-service enabled in Gold from day 1.

Delta Lake · Parquet · Schema evolution
SQL databases were abandoned for data storage in favor of a Delta Lake over ADLS Gen2. Parquet and Delta files handle each source's schema evolution particularities without costly migration pipelines.

Delta format brings ACID transactions, time travel and change data feed. Each source manages its own schema evolution without impacting other domains.
Synapse Serverless · Performance without clusters
Instead of keeping SQL clusters running, Synapse Serverless was adopted to query Parquet and Delta files directly from the lake. The project doesn't handle big data volumes that justify dedicated clusters, so Serverless delivers lake power at significantly lower cost without sacrificing performance.

SQL databases were reserved for cases with very low latency requirements or transactional application connectivity.
FinOps · Cost visibility, governance and optimization
Defined and managed the FinOps strategy for the data area, covering three pillars:
01
Visibility
Standardized tagging policies across all Azure resources aligned with the infrastructure team to attribute costs by domain, data product and environment.
02
Governance
Budgets and alerts per Landing Zone. Tagging policies are mandatory and validated in the CI pipeline — a resource without tags doesn't deploy.
03
Optimization
Migration from SQL databases to Synapse Serverless as the main cost reduction lever. Serverless pays per query, not per cluster uptime.
IaC · Terraform + Terragrunt
Implemented infrastructure as code with Terraform and Terragrunt, aligned with the organization's infrastructure team. Terragrunt manages module reuse across Landing Zones — dev, staging and prod environments are configurations of the same module, not independent stacks.

Tagging policies are part of the infrastructure code: any resource missing required tags fails the Terraform plan before deploying.
DevOps · Governance as code
Azure DevOps as active technical governance, not just CI/CD:

· Naming convention validation of data objects before merge
· Differentiated approval policies by impact (Silver Master changes require additional approval)
· Quality gates in every environment transition (dev → staging → prod)
· Mandatory tagging validated in pipeline before deployment
Data products — introducing the concept to the team
The biggest challenge wasn't technical: it was changing the team's mental model — from end-to-end projects per business requirement to reusable data products where a data product can be the source of another data product.

ADRs · Case 01
Architecture Decision Records · Azure platform
ADR-001
Centralized-federated model instead of full Data Mesh
Accepted
Context
Data Mesh principles were the right north star, but the organization lacked the maturity for domains to take autonomous data ownership. Adopting fully distributed self-service would have produced a platform with no real adoption.
Decision
The central data team builds all data products initially. The architecture is designed so domains can assume ownership without a redesign when ready. Self-service enabled in Gold from day 1, though not yet exploited. The architecture anticipates future maturity without demanding it now.
ADR-002
Delta Lake over ADLS Gen2 with Parquet as base format
Accepted
Context
Each source has its own schema evolution characteristics. Managing this with SQL databases required costly, fragile migration pipelines.
Decision and trade-off
Parquet as base format for interoperability, Delta for layers requiring ACID transactions and time travel. Schema evolution delegated to source level — each domain manages its own evolution without impacting others. Accepted trade-off: higher complexity in compaction and vacuum operations compared to SQL.
ADR-003
Synapse Serverless instead of dedicated SQL clusters
Accepted
Alternatives
Dedicated SQL clusters: better consistent latency, but fixed cost regardless of usage. Databricks: more powerful for big data and ML, but oversized for current volumes and more expensive operationally.
Decision
Synapse Serverless for the bulk of analytical queries — pay per query, no cluster management, no performance sacrifice for current volumes. Dedicated SQL reserved for specific low-latency requirements. Accepted trade-off: cold start latency on first queries of the day.
ADR-004
Terraform + Terragrunt as IaC standard with mandatory tagging
Accepted
Decision
Terraform aligned with the organization's infrastructure team. Terragrunt to manage module reuse across Landing Zones avoiding duplication. Tagging policies are part of the code — a resource without required tags fails the Terraform plan. This closes the FinOps loop: no tags, no deployment; no deployment, no unattributed resources.
ADR-005
Decouple Silver from Gold — two variants with different purposes
Accepted
Context
In the sandbox, Silver and Gold were intertwined. The coupling was invisible until migration was attempted — then it became the primary barrier.
Decision
Silver Master (shared master data, source for multiple Gold products, additional approval required for changes) and Silver Specific (per use case, no reuse obligation). Gold only consumes from Silver via explicit contracts, never directly from Bronze.

Learnings · Case 01
Azure · CAF Landing Zones · Delta Lake · FinOps
The biggest challenge
"The hardest part wasn't designing the architecture — it was changing the team's mental model: shifting from delivering end-to-end projects per business requirement to building data products that other data products would consume."
01
Concept before technology
Before configuring a single Landing Zone, I had to explain what a data product is and why it differs from a business pipeline. Without that shared understanding, any architectural decision was incomprehensible to the team.
02
Coupling is invisible debt until it hurts
The coupling between Silver and Gold in the sandbox wasn't obvious until migration was attempted. Explicitly documenting layer dependencies from the initial design would have saved weeks of impact analysis.
03
Adopt the real maturity level, not the ideal
Full Data Mesh was the right architecture on paper. Centralizing it in the data team was the right decision in practice. Good design isn't the most advanced — it's the one the organization can operate and evolve.
04
FinOps is easier to design than to sustain
The FinOps strategy with tagging policies in IaC works well at initial deployment. The real challenge is maintaining discipline as the team grows. Policies must be technically impossible to bypass, not just documented.
05
DevOps as governance is a cultural decision
Automatic naming validations generated initial resistance — the team saw them as friction. The shift was framing them as protection of the collective standard. Adoption came when the first error was caught automatically before reaching production.
06
What I'd do differently: data contracts from day 1
Formal data contracts arrived late. Without defining what each data product promises (frequency, completeness, latency), consumer expectations diverge from producer commitments in ways only discovered in production.
Case Study 02 · Snowflake

Snowflake + dbt + Iceberg
Snowflake · dbt · Apache Iceberg · Astronomer · Atlan · Microsoft Fabric · Terraform
Snowflake · dbt · Apache Iceberg · Astronomer · Atlan · Fabric · Terraform · DevOps
Designing and implementing a new data mesh
architecture on a completely new stack
Without prior experience in the stack but with intensive self-study, a modern platform was designed and implemented capable of absorbing migrations from both the original sandbox and the Azure distributed platform, while maintaining future interoperability with Azure via Apache Iceberg.
The starting point
Unlike the previous case, this project required designing and implementing on a completely new technology stack — Snowflake, dbt, Iceberg, Airflow — with no prior experience in any of these tools. The process required intensive learning in parallel with implementation.

The platform had to absorb two simultaneous migrations: solutions remaining in the original sandbox and solutions already built on the Azure distributed platform.
The same problems, new context
Migrating to the new platform meant facing the same structural challenges: layer coupling, teams accustomed to end-to-end projects, and the need to re-explain the data products model in a different environment.

Added complexity: maintaining interoperability with Azure for Data Science use cases and ML models that would remain in the Azure ecosystem.
Stack decisions — why each tool
Snowflake
Main compute and storage engine. Roles and warehouses managed as independent data products — each domain has its own warehouse sized to its actual workload.
Trade-off: vendor lock-in partially mitigated with Iceberg for lake data.
dbt (Data Build Tool)
Transformation layer with versioning, quality tests and documentation as code. Automatically generates the lineage consumed by Atlan. Custom best practices defined and documented for the team.
Trade-off: learning curve for the team, but the return in maintainability justifies the investment.
Apache Iceberg
Snowflake doesn't natively support Delta files. Iceberg as an open table format maintains interoperability with Azure: data scientists can consume data from Azure without depending on Snowflake. Parquet is maintained with the same goal.
Trade-off: higher operational complexity than Delta, but vendor independence justifies the cost.
Astronomer (Airflow)
Managed Airflow via Astronomer to avoid direct Docker and Kubernetes management. Configured with a data mesh approach. Astronomer's AI capability generated the v1.0 of minimal DAGs to orchestrate Data Factory, dbt and Power BI.
Trade-off: Astronomer cost vs savings in infra operations — favorable for the current team size.
Atlan
Metadata and governance platform integrated with Snowflake and dbt. Provides automatic end-to-end lineage from dbt, data quality checks and an active data catalog. Replaces the role Purview played in Azure.
Trade-off: higher license cost than open source alternatives, offset by native dbt and Snowflake integration.
Microsoft Fabric (Power BI only)
Migrating from Analysis Services to Power BI semantic models required Fabric for licensing. Fabric was enabled exclusively for Power BI, without expanding its use to the rest of the data platform. Snowflake remains the central engine.
Deliberate decision to avoid platform fragmentation.
Terraform · Azure and Snowflake deployment
Terraform maintained as IaC for two use cases:

· Azure deployments: resources remaining in Azure (Data Factory, networking, storage) continue managed by Terraform.

· Databases as data products in Snowflake: provisioning of databases, schemas, warehouses and roles managed through Azure DevOps pipelines with Terraform — treating Snowflake infrastructure with the same rigor as Azure.
DevOps · Governance as code across three platforms
The governance model was extended to the new stack, covering three platforms:

· Data Factory: pipeline naming and structure validation
· Snowflake: object, role and convention validation before deployment
· dbt: quality tests and documentation as a merge requirement — a model without tests doesn't pass the pipeline

Governance as code applied consistently regardless of the underlying platform.

ADRs · Case 02
Architecture Decision Records · Snowflake platform
ADR-006
Apache Iceberg as table format instead of Delta
Accepted
Context
Snowflake doesn't natively support Delta files. Data scientists and ML models would remain in Azure and needed to access lake data without depending on Snowflake.
Alternatives
Pure Parquet: maximum interoperability but no ACID transactions or time travel. Snowflake proprietary formats: maximum integration but total lock-in — any future migration would require re-exporting everything.
Decision
Iceberg as open table format for lake layers. Maintains interoperability with Azure (direct reading from Spark, Databricks or any compatible engine) without depending on Snowflake as intermediary. Parquet maintained as complement for read-only cases. Higher operational complexity of Iceberg is accepted.
ADR-007
Astronomer as managed Airflow platform
Accepted
Context
Self-managed Airflow requires maintaining Docker and Kubernetes. The data team doesn't have that operations profile, and the cost of dedicating time to orchestration infrastructure wasn't justified.
Decision
Astronomer as managed platform. Eliminates Docker and Kubernetes management from the data team. Astronomer's AI capability was used to generate the v1.0 of minimal orchestration DAGs — Data Factory, dbt and Power BI — accelerating time to first production pipeline. DAGs versioned in DevOps with the same policies as the rest of the code.
ADR-008
Snowflake warehouses and roles as independent data products
Accepted
Context
A single shared warehouse for the entire organization mixes workloads and makes it impossible to attribute compute costs by domain.
Decision
Each domain has its own warehouse sized to its actual workload. The role model follows least privilege: each data product has its own read/write roles, provisioned via Terraform through DevOps pipelines. Snowflake and dbt best practices formally documented for the team.
ADR-009
Microsoft Fabric enabled exclusively for Power BI
Accepted
Context
Migrating from Analysis Services to Power BI semantic models required Fabric for licensing. Fabric offers its own data platform capabilities that could duplicate Snowflake functionality.
Decision
Fabric enabled exclusively for Power BI and semantic models. Not expanded as a data platform — Snowflake remains the central engine. This avoids platform fragmentation and keeps Snowflake as single source of truth for analytical data. Not fully utilizing the Fabric license is accepted.
ADR-010
Atlan as governance, lineage and data quality platform
Open for review
Trade-off documented
Atlan integrates natively with Snowflake and dbt, automatically generating end-to-end lineage from dbt code without manual configuration. Alternatives (DataHub, OpenMetadata) require more integration and maintenance effort. Atlan chosen prioritizing time-to-value and dbt integration quality, with awareness of the higher license cost. Will be revisited when the number of active domains justifies reassessing ROI.

Learnings · Case 02
Snowflake · dbt · Iceberg · Astronomer · Atlan · Fabric
The repeating lesson
"The problems in the second migration were the same as the first — invisible coupling, mental models to change, governance that arrives late. The technology stack changes; the organizational challenges don't."
01
Learning the stack while implementing is viable
Intensive learning in parallel with implementation works if the conceptual design is clear from the start. Not knowing Snowflake or dbt didn't prevent making the right architectural decisions — trade-off reasoning transfers across technologies.
02
Interoperability must be designed, not added later
Choosing Iceberg over Delta was an uncomfortable decision — it adds operational complexity. But designing Azure interoperability from the start for data scientists is far less costly than adding it when data is already in production.
03
Governance as code scales; manual review doesn't
Applying the same DevOps governance model across three different platforms (Data Factory, Snowflake, dbt) proved that the pattern is technology-agnostic. What scales is the principle, not the specific configuration of each tool.
04
Managing tool scope is an architectural decision
Enabling Fabric only for Power BI, when it offers full data platform capabilities, was a deliberate decision to avoid fragmentation. Explicitly defining what each tool does is as important as choosing the tools.
05
Documented best practices are infrastructure
Formally defining Snowflake and dbt best practices for the team wasn't secondary documentation — it was a condition for the model to work. Without written standards, everyone interprets conventions differently and the data products model loses coherence.
06
What I'd do differently: formalize SLAs before scaling
When migrating two platforms simultaneously, data contracts were deprioritized in favor of operational readiness. With more active domains, the absence of formal SLAs generates friction that's difficult to resolve without renegotiating agreements from scratch.
